# Technology decision: formal-LTS standalone runtime

The standalone evaluation stack uses Docker containers for the API and PostgreSQL. Node 24 has an official LTS release line, and PostgreSQL 18 has a published five-year support window. These are free, self-hosted runtime services. The operator owns application maintenance and must publish a support and patch policy before any production release. [Node release schedule](https://nodejs.org/en/about/previous-releases), [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/).

The implemented secure-viewer slice now has local Ed25519 license signing, tenant-derived AES-256-GCM content-key wrapping, local operator-issued EdDSA access tokens, and encrypted package bytes in PostgreSQL. These remove mandatory OpenBao, external OIDC, and S3 services from the standalone Compose path. The signing and wrapping files must be backed up with the database; local key rotation and account recovery are not complete.

OpenBao Transit, S3-compatible storage (previously tested with SeaweedFS), and external OIDC remain optional adapters. The [OpenBao community support policy](https://openbao.org/community/policies/support/) is best effort and does not provide the formal LTS commitment required for this deployment. The [SeaweedFS community support page](https://www.seaweedfs.com/docs/support/) does not establish an equivalent formal LTS commitment. These adapters are excluded from the strict-LTS Compose runtime.

The Stripe adapter follows the documented [PaymentIntent creation](https://docs.stripe.com/api/payment_intents/create) and [webhook signature verification](https://docs.stripe.com/webhooks/signature) flows. It has offline tests for idempotency, order metadata/amount matching, signed raw webhook bytes, and full payment. Stripe is an external payment service, and a real checkout requires an account, fees, an order/entitlement state machine, refunds, reconciliation, and provider testing. No gateway-neutral offline mechanism can execute a real card payment independently of a payment network.

The generic secure-viewer package is not Widevine, FairPlay, or PlayReady. Those systems need commercial program access, protected clients, and certification. The optional Axinom adapter is inactive in the API runtime and does not establish provider certification.
